Approach

How I Choose the Right Tool

Most Salesforce decisions are trade-offs. These are the three I weigh most often.

OmniStudio vs. LWC

OmniStudio for guided, multi-step, data-driven journeys that admins will maintain (OmniScript + Integration Procedures).

LWC when the UI needs custom interaction, fine performance control or reuse across pages.

Record-Triggered Flow vs. Apex Trigger

Flow for simple field updates and record creation that admins can read and change.

Apex for complex branching, bulk-safe collections, unit tests and tight governor-limit control.

Queueable / Batch vs. Platform Events

Queueable or Batch for deferred or high-volume work that one org owns end to end.

Platform Events to decouple publishers from subscribers or notify external systems.

Three conceptual scenarios

Because I build in Apex, Flow, LWC and OmniStudio, I treat the agent as the conversational layer and keep decisions in testable, deterministic logic.

Case triage

Context: Looks up the case, its history and entitlement.

Action: A Flow checks SLA rules, then the agent drafts a reply or runs one scoped step, such as raising priority.

Guardrails: Invocable Apex with validated inputs, running with the user's permissions and sharing.

Guided intake

Context: Collects structured details one question at a time.

Action: Flow validates each answer and creates the record cleanly.

Guardrails: Complex exceptions hand off to an OmniScript or Flow screen instead of the agent improvising.

Human escalation

Context: Low confidence, or a sensitive request such as a high-value refund.

Action: The agent stops, summarizes the conversation and routes to a person.

Guardrails: Clear escalation topics and a queue owner, so nothing is left unanswered.

Engineering practice

How I Think About Code

Patterns and implementation principles that support maintainable, secure Salesforce solutions.

APEX DESIGN01

Thin trigger, focused handler

Keep trigger entry points small. Move decisions into handler or service classes so logic is easier to test, reuse and reason about.

trigger CaseTrigger on Case (
    before insert, before update,
    after insert, after update
) {
    CaseTriggerHandler.run(
        Trigger.operationType,
        Trigger.new,
        Trigger.oldMap
    );
}

Illustrative structure — adapt handler methods to the org's framework and trigger events.

BULK PROCESSING02

Design for collections

Process records as collections, query outside loops, use maps for lookups and plan asynchronous work for large data volumes.

  • Bulk-safe SOQL and DML
  • Batch / Queueable Apex where appropriate
  • Idempotency and partial-failure handling
  • Governor-limit-aware testing
LWC & UI03

Keep components focused

Use clear component boundaries, wire or imperative Apex based on the interaction, and communicate through documented events and public APIs.

  • Reusable, single-purpose components
  • Loading, empty and error states
  • Accessible controls and SLDS conventions
  • Server-side security remains authoritative
INTEGRATION04

Make integrations resilient

Use Named Credentials for endpoint authentication, validate payloads, handle timeouts and design observable failure paths.

  • REST / SOAP and JSON / XML
  • Platform Events for event-driven use cases
  • Retry strategy with duplicate protection
  • Useful logs without exposing secrets
SECURITY05

Security is part of the design

Respect the org's sharing model and enforce object- and field-level access. Validate authorization at the server boundary.

  • Sharing and access design
  • CRUD / FLS enforcement
  • Least-privilege permissions
  • Negative-path security tests
DELIVERY06

Make releases repeatable

Use version control, peer review, validation and automated deployment steps to reduce release risk across Salesforce environments.

  • Git branching and pull requests
  • SFDX / Salesforce CLI
  • Azure DevOps YAML pipelines
  • Test results and deployment traceability
